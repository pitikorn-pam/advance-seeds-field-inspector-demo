## MODIFIED Requirements

### Requirement: Postgres schema
The backend SHALL provide tables `profiles`, `varieties`, `calibration_profiles`, `inspections`, `seeds`, `recordings`, and `notifications` with foreign keys and enum types as defined by `supabase/migrations`. `varieties` SHALL include nullable `grade_criteria jsonb` for A-H measurement ranges. Existing nullable `inspections.batch_id` data may remain for historical compatibility, and new class-first mobile inspections do not require a single inspection-level variety.

#### Scenario: Schema applied cleanly
- **WHEN** an operator applies the `supabase/migrations/` directory to a fresh Supabase project
- **THEN** the active inspection tables exist with their columns, foreign keys, and enums
- **AND** `inspections.variety_id` accepts null for class-first captures
- **AND** `seeds` includes nullable class identity columns for model-backed detections
- **AND** RLS is enabled on every table

#### Scenario: Seed rows preserve detected class identity
- **WHEN** a model-backed inspection inserts seed rows with detected class data
- **THEN** each seed row can store `class_id`
- **AND** each seed row can store `class_name`
- **AND** rows from legacy inspections may leave those columns null

### Requirement: Role-based row-level security
The backend SHALL enforce that an authenticated user with role `inspector` cannot read or modify rows owned by another user, that `admin` can read all rows, and that destructive permissions remain scoped by resource type. New class-first columns SHALL NOT change inspection ownership or seed access rules.

#### Scenario: Inspector cannot read another inspector's class-first inspection
- **GIVEN** Jane is signed in as inspector
- **WHEN** she queries inspections or seeds belonging to Alex
- **THEN** she receives zero rows even when those rows include class identity fields

#### Scenario: Admin reads everything
- **GIVEN** Alex is signed in as admin
- **WHEN** he queries `select * from inspections`
- **THEN** he sees both his own and Jane's inspections

#### Scenario: Admin cannot delete another's inspection
- **GIVEN** Alex is admin and inspection X is owned by Jane
- **WHEN** he attempts to delete X
- **THEN** the delete is denied by RLS

#### Scenario: Admin can delete recordings
- **GIVEN** Alex is signed in as admin
- **WHEN** he deletes a recording row or its object in the `recordings` storage bucket
- **THEN** the delete is allowed by the recording-specific RLS/storage policies
- **AND** inspection rows that referenced the recording remain intact

### Requirement: Generated TypeScript types
The backend SHALL expose generated TypeScript types in `packages/types/src/supabase.gen.ts` regenerated by `pnpm supabase:types`.

#### Scenario: Types regenerate after class-first schema change
- **WHEN** `inspections.variety_id` is relaxed and seed class columns are added
- **AND** `pnpm supabase:types` runs
- **THEN** the regenerated file includes nullable `inspections.variety_id`
- **AND** it includes nullable seed class identity columns on the `seeds` row type
