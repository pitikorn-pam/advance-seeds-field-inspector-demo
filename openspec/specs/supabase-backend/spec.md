# supabase-backend Specification

## Purpose
Define the Supabase schema, storage buckets, RLS policies, seed data, and generated type contract used by the mobile field-inspector demo.
## Requirements
### Requirement: Postgres schema
The backend SHALL provide tables `profiles`, `varieties`, `calibration_profiles`, `inspections`, `seeds`, `recordings`, and `notifications` with foreign keys and enum types as defined by `supabase/migrations`. `varieties` SHALL include nullable `grade_criteria jsonb` for A-H measurement ranges. Existing nullable `inspections.batch_id` data may remain for historical compatibility, but new mobile inspections do not set it.

#### Scenario: Schema applied cleanly
- **WHEN** an operator applies the `supabase/migrations/` directory to a fresh Supabase project
- **THEN** the active inspection tables exist with their columns, foreign keys, and enums
- **AND** RLS is enabled on every table

### Requirement: Role-based row-level security
The backend SHALL enforce that an authenticated user with role `inspector` cannot read or modify rows owned by another user, that `admin` can read all rows, and that destructive permissions remain scoped by resource type.

#### Scenario: Inspector cannot read another inspector's inspection
- **GIVEN** Jane is signed in as inspector
- **WHEN** she queries `select * from inspections where inspector_id = <Alex's id>`
- **THEN** she receives zero rows

#### Scenario: Admin reads everything
- **GIVEN** Alex is signed in as admin
- **WHEN** he queries `select * from inspections`
- **THEN** he sees both his own and Jane's inspections

#### Scenario: Admin cannot delete another's inspection
- **GIVEN** Alex is signed in as admin
- **WHEN** he attempts to delete one of Jane's inspections
- **THEN** the delete is denied by RLS

#### Scenario: Admin can delete recordings
- **GIVEN** Alex is signed in as admin
- **WHEN** he deletes a recording row or its object in the `recordings` storage bucket
- **THEN** the delete is allowed by the recording-specific RLS/storage policies
- **AND** inspection rows that referenced the recording remain intact

### Requirement: Seeded reference data and demo users
The backend SHALL be seeded with two demo users (`jane@advanceseeds.com` inspector, `alex@advanceseeds.com` admin), 6 varieties, 2 calibration profiles, and at least 7 inspections with child seeds rows, after running the seed scripts.

#### Scenario: Seed script idempotency
- **WHEN** the seed script runs twice
- **THEN** the second run does not create duplicate users or duplicate reference rows

#### Scenario: Inspection has child seeds
- **WHEN** an admin queries any seeded inspection
- **THEN** it has between 8 and 24 child rows in `seeds` with non-null length, width, area, and grade

### Requirement: Media storage buckets
The backend SHALL provide `inspection-images` and `recordings` storage buckets with authenticated write and public read for the demo.

#### Scenario: Authenticated upload, public render
- **WHEN** a signed-in user uploads an image to `inspection-images/<uuid>.jpg`
- **THEN** any client (signed in or not) can render the image via the returned public URL

#### Scenario: Recording object policy
- **WHEN** a signed-in user uploads a video to `recordings/<path>.mp4`
- **THEN** any client can render it via the returned public URL
- **AND** owner or admin delete policies can remove it when the app deletes a recording

### Requirement: Generated TypeScript types
The backend SHALL expose generated TypeScript types in `packages/types/src/supabase.gen.ts` regenerated by `pnpm supabase:types`.

#### Scenario: Types regenerate after schema change
- **WHEN** a column is added to `inspections` and `pnpm supabase:types` runs
- **THEN** the regenerated file includes the new column on the `inspections` row type
