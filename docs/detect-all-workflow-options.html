Advance Seeds Field Inspector

Workflow ตรวจจับทุก Class: สรุปปัญหาและทางเลือก

Workflow ปัจจุบันยังตั้งอยู่บนสมมติฐานว่า user ต้องเลือก variety ก่อนเริ่มตรวจ แต่ทิศทางใหม่คือ class-first workflow: model ตรวจจับ class ที่ train มาได้ทั้งหมด และ user เลือก filter ได้ว่าจะดูทุก class หรือเฉพาะ class เช่น banana หรือ watermelon

TL;DR

ตัว model สามารถคืนผลหลาย class ได้อยู่แล้ว ข้อจำกัดตอนนี้อยู่ที่ workflow ของ app: app ยังบังคับให้เลือก variety ก่อน และใช้ variety นั้นไป filter ผล detect ตั้งแต่ต้น ทำให้ class อื่นที่ model เห็นถูกซ่อนออกจาก pipeline

ทิศทางที่แนะนำคือเปลี่ยน inspection ให้เป็น class-first: user เลือก ALL หรือเลือก detector class เป็น filter, live และ post-shutter analysis ใช้ filter เดียวกัน และหน้า inspection detail สามารถกรอง thumbnail ราย seed/object ตาม class ที่ detect ได้

เรื่องที่ต้องตัดสินใจ

จะทำรอบแรกแบบ metadata-only เพื่อให้เร็ว หรือเพิ่มการ persist class ต่อ seed/object ตั้งแต่ตอนนี้เพื่อให้ reload, filter, และ reporting ถูกต้องตั้งแต่ต้น

แนะนำ: เก็บ class ต่อ seed/object

Flow ที่คาดหวัง

1. เปิดแอพ User เข้า app แล้วเลือก Inspect
2. เลือก filter เลือก ALL, banana, watermelon หรือ class อื่นที่ model train มา
3. Live detect ALL overlay ทุก class; ถ้าเลือก class เฉพาะก็ overlay เฉพาะ class นั้น
4. Snap Post-shutter analysis รันซ้ำด้วย filter เดียวกับ live
5. Review/detail Thumbnail ราย seed/object กรองตาม class/variety ได้

ปัญหาปัจจุบัน

  • Workflow ไม่ตรงกับ model: app บังคับเลือก variety ก่อนตรวจ แต่ผลจาก model เป็น class-based และหนึ่ง frame สามารถมีหลาย class ได้
  • Filter เร็วเกินไป: variety ที่เลือกถูกแปลงเป็น model class filter ตั้งแต่ก่อน live/post-shutter analysis ทำให้ class ที่ไม่ได้เลือกถูกซ่อน
  • Data model ไม่พอ: database ตอนนี้ผูก variety หนึ่งตัวที่ระดับ inspection แต่ requirement ใหม่ต้องรู้ class ของ object แต่ละชิ้น
  • หน้า detail ยัง filter ไม่ได้อย่างถูกต้อง: การ filter thumbnail ราย seed/object ตาม class ต้องมี class ติดอยู่กับแต่ละ seed หลัง save และ reload

ทางเลือกของ Solution

ทางเลือก สิ่งที่จะทำ ข้อดี ความเสี่ยง / Trade-off ความเหมาะสม
A. Metadata-only เพิ่ม ALL/class filter ใน capture, detect ทุก class และเก็บ class breakdown ไว้ใน metadata ของ inspection เร็วที่สุด แตะ schema น้อย เหมาะกับการพิสูจน์ live/post pipeline การ filter ราย seed หลัง reload จะเปราะ เพราะ class ไม่ได้ติดอยู่กับ seed row โดยตรง เหมาะเป็น demo ระยะสั้น
B. Per-seed class persistence เพิ่ม ALL/class filter และเก็บ class id/name ของ seed/object แต่ละชิ้น พร้อมเก็บ class breakdown ระดับ inspection เป็น summary metadata Data model ถูกกับ requirement: filter thumbnail ได้, รองรับ reporting ในอนาคต, และรองรับ inspection ที่มีหลาย class ต้องอัปเดต schema, generated types, save payload, offline sync และหน้า detail/report แนะนำ
C. Multi-variety inspection only เก็บ array/list ของ variety ที่ระดับ inspection โดยไม่เก็บ class ของ seed/object แต่ละชิ้น บอกได้ว่า inspection นี้มีหลาย class/variety ไม่ตอบว่า seed/object ไหนเป็น class ไหน จึงไม่พอกับ requirement filter thumbnail ราย seed ไม่พอ

ข้อแนะนำ

เดินต่อด้วย Option B: Per-seed class persistence เพราะตรงกับ behavior ที่ต้องการ: model detect เป็น class, UI filter ตาม detected class และหน้า inspection detail filter thumbnail ได้อย่างถูกต้องหลัง reload

Scope แรกควรโฟกัสที่ class filter selection, parity ระหว่าง live/post-shutter, การเก็บ class ต่อ seed/object, class breakdown metadata และ detail-page filtering ส่วน redesign reporting เชิงลึกควร defer จน capture result stable แล้ว

รูปแบบ Implementation

Capture UX

เปลี่ยนจาก required variety selection เป็น detector filter selection: ALL หรือ model class group

Analyzer Pipeline

ถ้าเลือก ALL จะไม่ส่ง class filter ถ้าเลือก class เฉพาะจึงส่ง class id เฉพาะชุดนั้น

Persistence

Save class id/name ต่อ seed/object และเก็บ class breakdown ระดับ inspection สำหรับ summary/reporting

Inspection Detail

เพิ่ม filter chips สำหรับ All และแต่ละ detected class โดย thumbnail list ใช้ข้อมูล class ที่ save มากับ seed/object

Backward Compatibility

Inspection เก่าที่ไม่มี class data ต้องยังแสดงผลได้ตามเดิม โดยซ่อนหรือ disable class filter

Validation

Test ALL mode, single-class mode, parity ของ post-shutter, save/reload และ detail-page thumbnail filtering

ความเสี่ยงและ Mitigation

ความเสี่ยง ผลกระทบ Mitigation
Schema และ offline sync เปลี่ยน Save/offline replay อาจพังถ้า payload ไม่ตรงกัน อัปเดต schema, generated types, save payload และ queue replay ใน change เดียว
Inspection เก่าไม่มี class data Row เก่าไม่สามารถ filter ตาม class ได้ Render row เก่าตามเดิม และแสดง class filter เฉพาะเมื่อมี class data
Grading ต่อ class หนึ่ง inspection อาจมี class ที่ใช้ grading rule ต่างกัน รอบแรกใช้ generic fallback หรือ mapped class rules เท่าที่มี และบันทึก rule ที่ใช้ไว้ใน metadata
Class name ไม่ตรงกับชื่อ product ชื่อ class จาก model อาจไม่ตรงกับชื่อที่ user คุ้นเคย ใช้ model class name เป็น source of truth และมี display mapping ผ่าน reference data เมื่อจำเป็น

Next Decision

ถ้า leadership/product เห็นด้วยกับ Option B ขั้นต่อไปคือสร้าง implementation spec สำหรับ detect-all class-first inspection workflow และแยกงานเป็น capture UX, analyzer wiring, persistence, detail filtering และ compatibility testing
